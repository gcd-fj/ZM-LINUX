# 性能采样与验收

性能结论以相同条件的 release 测量为依据。宿主更新频率、源 SWF 帧率和渲染提交频率含义不同；CPU 提交时间也不能作为 GPU 执行时间。下面的采样工具只统计指定进程及其线程，不包括子进程、合成器或 GPU。

## 组队关卡与调度修正（2026-09-14）

用户再次复测组队关卡 HARD_1-21_V327：北京时间 20:49:19–20:49:59 的多个约 5 秒区间只有 15–22 次渲染提交/秒，最低约 15.10 次/秒；之后连续多个区间恢复约 30 次/秒。此频率按累计渲染提交次数差分计算，不能替代 GPU 实际呈现 FPS。播放器 tick 窗口 p95 达 40.82ms、峰值 334.63ms，输入阶段另有 613.10ms 峰值；输入分发也会执行游戏事件处理。渲染提交 CPU p95 约 5–8ms。

这段新增的 74 次资源就绪全部命中缓存，累计下载数没有增加；因此持续的战斗掉帧不能主要归因于下载。地图 SWF 从缓存就绪约 11.72ms，随后关联本地任务约 62.17ms。不同窗口的峰值会重复出现，并不表示每 5 秒重新发生一次停顿。采样与限定见 `target/perf/team-20260914-1249-report.md`；用户手动操作，采样结束仅停止自建采样脚本，未关闭游戏。

代码复现发现宿主会用 **tick 完成时间** 计算下一个完整刷新时机。若 tick 跨过下一时机，宿主再次跳过它、继续等待；Ruffle 按实际经过时间补帧，可能使负载陷入“两次游戏帧对应一次渲染”的循环。修复改为用 **tick 开始时间** 推进截止时间，已在执行期间到期的下一时机不再被额外跳过。

确定性回归模型为：30Hz、每游戏帧 12ms、每 tick 额外处理 12ms、提交 2ms，以及一次 100ms 停顿。单帧共 26ms，可维持目标；两帧 tick 为 36ms，会跨过截止时间。模型恢复窗口内，旧策略约 15 次提交/秒，新策略约 30 次/秒，执行的游戏帧数基本一致。该结果证明宿主的放大机制，不是修复后真实游戏性能数据。实际经过时间、Ruffle 补帧上限、游戏帧率和脚本计时未修改；数百毫秒的单次任务仍需进一步分析。

Linux 工作区 109 个测试、严格 Clippy、格式与差异检查、release 构建通过；记录为 `target/perf/team-scheduler-workspace-tests.txt`、`team-scheduler-clippy.txt`、`team-scheduler-release.txt`。用户随后重跑组队关卡，反馈有明显改善；这是实机定性反馈，尚未取得受控前后对照数据，不能据此承诺提速比例或宣称所有长停顿均已解决。本轮未运行 Windows 验证。

## 加载提示与实机记录（2026-09-14）

状态栏改为固定 36pt 高度、紧凑的金色三点提示，使用固定文案“资源加载”。数量和累计接收量移入悬停详情：计数变化不再改变提示宽度，左侧状态文字固定左对齐；读取不足 180ms 不闪现，连续请求间隔不足 600ms 时保留提示。等待间隙的待完成数准确显示为 0，停止游戏时清空显示状态。准备阶段合并资源完成与初始化的普通提示，错误仍可见。

原 `egui::Spinner` 默认使用主题 40pt 控件高度，并在每次绘制时请求立即重绘。新提示仅由现有游戏帧驱动，不自行请求重绘。回归覆盖游戏截止时间不被动画覆盖、请求数量变化时状态栏高度固定、短请求抑制与连续请求的平滑显示。使用实际 egui 布局和字体做了离屏预览检查。

原“已接收 N.N MiB”是本次会话累计收到的资源响应体大小，排除缓存命中、包含重试，既不是 MiB/s，也不是网络包大小。库交付响应体分片时更新计数，不能据此推断 TCP 包尺寸。新增 HTTP 响应头等待与响应体接收计时：前者包括连接、重定向和等待响应头，后者包括接收、自动解压及进度回调；失败和取消阶段也计入，二者不是纯服务器耗时或纯线路速度。资源就绪日志增加字节数和 `ready_wait_ms`；该时间还包含缓存锁、发布及本地主线程恢复轮询的等待。

## 造五组队噩梦掉帧跟进（2026-09-12）

用户报告组队噩梦战斗严重掉帧，结束后掉落物迟迟出现。结合该次本地日志与随后提供的诊断，确认以下证据：

- 战斗日志中噩梦 Boss 出现 `Skipping cacheAsBitmap`，边界为 **6,710,075 × 6,710,648 像素**。空且可见的子对象仍可带滤镜；滤镜扩展了 `Rectangle::INVALID` 的哨兵坐标，令父对象边界异常巨大。已用实际 MovieClip 与模糊/发光滤镜复现，修复为仅扩展有效边界。该问题会使位图缓存失效，但日志本身不能量化其战斗耗时占比。
- 随后复制的诊断来自约 **8.8 秒的启动/主界面会话**，不是先前整场战斗：19 次缓存命中、0 次下载，一次本地任务轮询耗时 **1535.332ms**，调度延迟峰值 **1529.631ms**；缓存读取峰值仅 **15.207ms**。早期长任务已被最近 1200 个样本挤出，所以最近窗口的低峰值不能否定发生过停顿，也不能用这份短会话诊断判断噩梦战斗 FPS。
- 同一噩梦地图的第二段资源记录有 124 次完成，123 次命中缓存。记录到的掉落图标也命中缓存，该战斗段没有静态资源最终下载失败记录。这不证明所有掉落处理均已完成：游戏回调、对象创建和服务端消息仍需实机进一步定位。

另复现了 egui 0.33.3 会从 `request_repaint_after` 参数中减去预测帧间隔的行为。宿主原来传入的是距游戏绝对截止时间的剩余量，因此会提前唤醒，临近截止时间时可能反复请求零延迟更新。现在加回同一个预测间隔，让原生后端收到的等待时间等于剩余量；到期帧、输入和任务唤醒保持即时，未调整游戏目标帧率或脚本计时。真实 egui 回调测试覆盖上述行为；164Hz 宿主更新存在这一确定机制，但尚未采集修复后的战斗对照。

诊断补充会话时长、六阶段全会话峰值及其所在更新的开始时间，不受最近样本淘汰影响。本地 Future 单次执行达到 20ms 时记录任务编号、时间和关联资源，保存最近 8 次及全会话最慢一次，同时写入日志。关联来源在实际 poll 内标记，跨等待保持且嵌套 poll 后恢复；仅使用已校验静态资源路径（移除查询、片段、控制字符并限长）或固定网络类别，不记录认证请求内容。这里的关联资源不是独立解析阶段计时，耗时还可能包括游戏回调和 GC。

## 加载动画修正（四阶段优化后的补充）

用户实测反馈战斗更流畅，但造四/造五的加载条会长时间停在 0% 或 100%。确认宿主强制启用了 `LoadBehavior::Delayed`：只要还有电影尚未预加载完成，Ruffle 就会跳过游戏帧执行，进度条所在的时间线和重绘也一起等待。本次改用默认的 `Streaming` 加载模式，让已有游戏帧在依赖预加载期间继续执行；宿主帧率、任务轮询预算和渲染提交条件保持原有设置。

另为官方资源下载增加真实字节进度通知。窗口底部固定单行显示待完成的资源请求数与本次游戏会话累计接收的响应体 MiB，同时保留原状态/错误消息。统计不含缓存命中，包含重试期间实际再次接收的数据；已接收字节不等于压缩后的网络流量，也不是整场游戏的总进度。通知使用每个在途请求的一份小状态，直接更新聚合计数，不向 UI 消息队列逐分片追加事件。取消后观察者失效，各会话独立统计；原缓存原子发布和重试策略仍保留。

此改动解决了一个确定的预加载动画冻结原因，并提供真实下载活动反馈。它没有为 Ruffle 的 `Loader`、`URLLoader`、`Sound` 新增逐网络分片的 ActionScript `ProgressEvent`；这些路径仍可能等完整响应后才更新游戏自身的百分比。SWF 解压、图片解码和 `loadBytes` 的单次长任务也仍可能造成局部停顿，不能用外部 4ms 任务预算强行中断。后续应结合两款游戏的诊断数据定位，不能把底部资源接收量称为游戏加载完成度，或宣称已经达到 Windows 360 游戏大厅的加载速度。

自动验证：工作区 **95 个测试通过**，包含 2 个确定性加载回归、3 个现有 SWF 样例在宿主 Streaming 模式下的额外回归、真实 HTTP 分片/未知长度/重试/取消/并发缓存测试，以及观察者重复、乱序、取消后的计数测试。受控依赖未完成时，Streaming 能推进到已加载的第 2 帧并重绘，Delayed 保持第 0 帧；依赖完成后都能正常继续。Ruffle 位图缓存 2 个回归、格式检查、严格 Clippy 及 release 构建也通过。结果保存在 `target/perf/loading-fix-tests.txt` 与 `target/perf/loading-fix-release.txt`。下面的空闲 A/B 和日志微基准属于此前四阶段产物，不是这次加载修正后的测量。

声音反馈随后由用户确认为造四游戏内勾选了静音；本次没有音频改动。新版需要用户手动重启后复测两款游戏的加载动画、冷/热缓存场景和实际等待时间。

## 工具与隔离

工具仅依赖 Linux `/proc` 和 Python 3.11+ 标准库，不执行 shell。每次命令模式运行创建独立的 XDG 配置、缓存、数据和状态目录；不会读取原有的 ZM-LINUX 配置。`--xdg-root` 可复用专门的测试目录以测量热缓存，切勿指向日常用户目录。XDG 隔离不是网络隔离；工具本身不会登录账号，游戏场景需要测试者在独立配置中手动登录。

```sh
# 先记录二进制哈希、工具链、CPU/GPU、显示环境和工作区版本。
python3 tools/perf-context.py --binary target/release/zm-linux --output target/perf/after/context.json

# 空闲登录页：预热 10 秒，采样 30 秒；每次使用全新的输出前缀。
python3 tools/perf-sample.py --output target/perf/after/idle-01 --warmup 10 --duration 30 --interval 0.25 -- target/release/zm-linux

# 游戏场景：手动进入指定场景并预热后，只读附加到已启动进程。
python3 tools/perf-sample.py --output target/perf/after/zm4-combat-01 --pid 12345 --warmup 0 --duration 60

# 本地小进程自测，不访问网络、不启动游戏。
python3 tools/perf-sample-test.py
```

输出包括 `.json` 汇总、`.csv` 原始样本，以及命令模式的 `.child.log` 与 `.xdg/` 测试目录。输出文件已存在时拒绝覆盖。命令行参数列表及完整环境不会写入报告；应用自己生成的日志仍按应用脱敏策略处理，分享前只选择所需的性能数据。

- CPU 均值为采样跨度内 CPU 时间除以墙钟时间；`100%` 代表占满一个逻辑核，多线程可超过 `100%`。p50/p95/p99 使用各采样间隔的 CPU 百分比，均值按总时间加权。
- `peak_sampled_rss_bytes` 为采样期间观测到的最大 RSS；`lifetime_peak_rss_bytes` 来自 VmHWM，包含预热及附加前的进程历史。短于采样间隔的内存尖峰可能遗漏。
- `rchar/wchar` 为读写系统调用字节数，包括缓存命中；`read_bytes/write_bytes` 为内核记账的存储 I/O，不能互相替代。无权限或计数不可用时报告 `null`。
- 默认最多 36,000 个样本，原始数据边采集边写出；到达时限或样本上限即结束，不因卡顿补采密集的过期样本。汇总的跨度为首尾成功采样之间的时间，不涵盖进程退出前未采到的尾部。
- 命令模式在到时或 Ctrl+C 后终止自己创建的进程组，并保存汇总；`--pid` 模式始终只读，不终止目标。SIGTERM 不等同于应用内“退出游戏”，不能替代返回登录页后查看诊断快照的手动验证。独立测试目录保留以供查看或复用。

## 内部诊断指标

`Frames (session)` 的 `source_fps` 是源 SWF 头中声明的原始帧率，`game_target_fps` 是播放器当前目标帧率，可被游戏通过 `Stage.frameRate` 动态修改。`update_hz` 是宿主播放器更新频率，`tick_hz` 是调用播放器 tick 的频率，`render_submissions` 是会话累计渲染提交次数；这些都不是通过 GPU 呈现统计得到的实际游戏 FPS。

`ui_update_cpu` 与各 `Player ... CPU wall` 统计主机调用的墙钟耗时，分别覆盖 UI 更新、播放器更新、输入、任务队列、tick 和渲染提交；这些值会包含线程被操作系统调度出去的等待，不能替代 `/proc` 的实际 CPU 时间。`Player schedule_late` 为调度迟到，`Local tasks (session)` 中的 `queued_tasks`、`peak_queue_depth`、`max_single_poll_ms` 分别表示剩余积压、峰值队列深度和最慢单次任务轮询；协作式轮询预算无法中断一个正在执行的长任务。

内部耗时保留最近 1,200 个样本，报告最近窗口的 p50/p95/p99、均值和峰值，`total_count` 保留累计计数。播放器六阶段另保留全会话峰值，慢任务另保留最近 8 次及全会话最慢一次；它们不改变窗口百分位的含义。内部百分位采用 nearest-rank，外部采样器采用线性插值，两者统计对象也不同。一次退出快照不会自动保存完整 60 秒的全部内部样本；需要较长场景时间序列时，按固定时点复制诊断，同时将打开诊断产生的开销作为独立场景控制。

`Asset performance` 跨该资源管理器的生命周期累计，涵盖两款游戏和失败/取消的尝试；切换游戏或清理缓存不重置统计。单次启动分析应使用新进程，或同时记录前后 `total_count` 和原始阶段日志，不能把混合历史的分位数归因于最后一次启动。

## 对照测量程序

对每个独立阶段保存 release 产物与 `perf-context.py` 输出，并用同一套参数交替运行旧版和新版。记录窗口实际尺寸、桌面缩放、显示刷新率、窗口焦点与遮挡、GPU/后端、电源设置、温度和其他负载。两边统一日志过滤器；固定测试场景、角色和操作路径。当前旧版空闲参考使用 `RUST_LOG=warn`；采集详细资源阶段日志时，两边统一改用所需的 info 过滤器并重测。

| 场景 | 每款游戏、每个版本的重复次数 | 记录内容 |
| --- | --- | --- |
| 冷启动 | 至少 5 次 | 认证成功至游戏可交互的总时间，以及资源校验、版本查询/网络、补丁、写盘、播放器构建的各阶段耗时；CPU、RSS、I/O |
| 热启动 | 至少 5 次 | 同上；确认使用相同版本的有效缓存，最新版检查仍执行 |
| 固定场景加载 | 预热后采样 60 秒，重复 3 次 | UI/输入/队列/tick/提交耗时分位数、调度延迟、队列积压、CPU、RSS、I/O |
| 固定战斗场景 | 预热后采样 60 秒，重复 3 次 | 同上；保持角色、技能、敌人和操作路径一致 |
| 诊断窗口关闭/打开 | 各采样 60 秒，重复 3 次 | 自动刷新频率、CPU与耗时变化；复制结果保持新鲜 |
| 连续切换游戏 | 在同一进程中交替切换 20 次 | 每次进入同一静止场景并等待相同时间，记录 RSS 及可用的 GPU 资源数据；检查是否持续增长 |

两款游戏分别为造梦西游 4 和造梦西游 5。这里的“冷”默认指**应用缓存为空**，不清空系统页缓存，也不执行全局 `drop_caches`。每次冷启动使用新的专门测试目录；热启动复用指定版本的测试缓存。记录官方资源版本、网络状态、缓存字节数及命中情况；官方更新或网络异常的运行单独标记，不能混入正常热启动均值。登录和验证码等待时间不计入认证后的资源/播放器准备时间。

冷启动需要用户在独立配置中使用有权测试的账号。测试者可在应用中先完成登录，再按同一路径进入游戏；不要自动读取已有凭据库或复制账号配置。为了观察完整人工流程，可以提前以较长时限启动命令模式，再对其 PID 运行 60 秒场景采样；附加采样结束不关闭游戏。

主 SWF 离线微基准可使用合法本地缓存的**资源文件副本**：固定输入哈希、版本、压缩格式与补丁版本，在专门测试目录重复执行校验/补丁，分别记录原始读取、哈希、解压、修改、压缩和原子发布时间。不得把账号配置、token 或私有日志当作基准输入；离线微基准不能替代含网络的真实启动时间。

对 5 次启动保留全部原始结果并报告中位数及范围；仅有 5 个样本时 p95/p99 不具有稳定的尾延迟意义。对每轮 60 秒场景报告内部有界耗时样本的 p50/p95/p99 和外部 CPU/RSS/I/O 汇总，再比较三轮一致性。只有观测收益大于重复运行的波动时才报告提速比例；异常、缺样和环境改变必须同时说明。

## 藏宝洞长停顿跟进（2026-09-14）

用户操作期间取得 317 秒、1269 个进程样本。相邻性能快照差分的最低约 5 秒区间为 16.60 次渲染提交/秒；另有零接收字节区间降至 18.55 次/秒。播放器 tick 窗口峰值最高 1610.52ms，渲染提交 CPU 窗口峰值最高 10.435ms。窗口统计会重叠，不把重复显示的峰值计为多次事件；这些数字也不是 GPU 执行耗时或实际呈现 FPS。

这说明下载不是所有卡顿的原因，但尚未证明脚本、资源预处理或 GC 中的哪一项是主要瓶颈。采样窗口可能包含后续面板操作，不能作为同条件优化前后对照。完整数值和边界说明保留于 `target/perf/treasure-cave-20260914-1330-report.md`。

为继续定位，`RUST_LOG='warn,zm_player=info,zm_perf=info'` 可额外记录大于等于 25ms 的播放器内部阶段（预加载、AVM 帧逻辑、定时器/网络回调、鼠标处理和 GC）。记录只有静态阶段名与墙钟耗时，不含脚本值或账号信息；阶段可以嵌套，耗时不可相加。默认关闭，不调整脚本计时、执行预算、帧率或 GC 策略。
